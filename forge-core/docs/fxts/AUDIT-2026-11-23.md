# FxTS audit, 2026-11-23: what a passing spec proves today

**Why this exists.** At gate 1 for BACKLOG FB-263 a module's spec, its manifest and its code were found to state three different sets of context fields. The owner, 2026-11-23: "These issues must be FULLY investigated. The use and functionality of FxTS is central to the forge framework and if they are not working as intended the consequences will continue to compound until fully remedied. No band-aids or work arounds. FxTS must be rock solid."

**How it was done.** Five read-only audits, one per part: the adapter specs (FACTS); the module specs and the conformance kit (FMTS); the hub's API specs and the transport specs (FATS, FTTS); the view, object and widget specs and the governed lists (FVTS, FUTS); and the machinery they share. Each was told to change nothing and to count a finding only when it was proved by running the real code or by a line of it. The four claims the conclusions rest on most were then read at the source by the session that wrote this page (§2.1, §2.2, §2.3). Nothing in the repository was changed by the audit.

**What it is not.** It is not a design. The fixes are BACKLOG FB-264 to FB-274 and the design that follows them. This page is the evidence; it is dated and is not kept current.

## 1. The finding

**A spec that passes does not mean the real thing agrees with it.** In every framework, most of what a spec declares is compared with the spec itself, or with another written statement, and never with the code or its behaviour. Where the real thing was measured, it disagrees.

What a pass proves today, by framework:

| Framework | A pass proves | A pass does not prove |
|---|---|---|
| FACTS (adapter) | the spec is well-formed against itself; its hash covers it | anything about the module's code. No check compares the two; the live checks are one stub that returns "skipped" |
| FMTS (module) | for some requirements, that files exist; for four, behaviour in an in-process kit with one failure injected | six requirements are decided from what the spec says about itself or are not checked; any requirement can be waived |
| FATS (hub API) | ten fields are present in the file | that the route exists, needs the authentication declared, returns the format declared or is limited as declared. The runner never applies the schema |
| FTTS (transport) | the file is self-consistent and three Python names import | anything about the proto, the servicer or the signed transport contract. The runner never opens a proto file and never applies the schema |
| FVTS, FUTS (views, widgets) | the file matches its schema, its references resolve, mirrored enums match the Python models | that the hub produces, serves or authorizes what is declared. Nothing renders it (forge-display is not built) |

## 2. The shared machinery

### 2.1 A check that did not run is a pass

- `FxTSReport.passed` is true when every verdict is PASS or SKIP (`forge_core/fxts/shared/runner.py`, the `passed` property). A report with no verdicts passes: `[PASS] 0/0`.
- `forge governance run fmts forge-wms` prints `[PASS] 25/29`, "All checks passed.", then four lines "Not checked", and exits 0.
- Live checks that were not asked for produce no verdict at all (FATS, FACTS, FTTS). Asked for, the FACTS live check is "not implemented" and the run passes.
- Any exception while loading a module in the FMTS runner becomes a skip: with the kit raising an error, the result is `[PASS] 21/29`.
- A runner with no schema path produces no `schema-current` verdict: a spec with no schema record gave `[PASS] 9/9`.
- An exception inside a runner's checks is not caught: the command ends in a traceback and no report. Specs with a value of the wrong type raised in five frameworks.

### 2.2 Nothing gates

- CI runs `ruff` and `pytest` (`.github/workflows/ci.yml`). No workflow and no Makefile target runs a `forge governance` command.
- `forge governance specs` never exits non-zero: with a hash mismatch it printed the mismatch and returned 0.
- **An approved spec that fails its runner is green.** On a copy of the repository, an adapter spec was edited, stamped and approved with the CLI; its run gave `[FAIL] 34/37`; the governance tests stayed green. No test asserts the failures of a full FACTS run for five of the modules; the FATS gate asserts only the two hash verdicts.
- The test of the ten baseline requirements (`tests/governance/test_framework_baseline.py`) observes a proxy for six of them. Proved by changes that break the property while the test passes: a framework's purpose replaced by filler text; a framework's gate replaced by an empty test file; a runner whose checks return nothing. F-7 has no test. F-5's search for stray files cannot match an adapter spec's file name.
- By the baseline record's own definition, "complete" is false for FATS and FTTS: neither runner reads its schema, so a spec the schema refuses can pass (17 of 35 and 63 of 200 schema-invalid mutations passed a run).
- FHTS is exempted as "infrastructure". It has code, no schema, no specs and no gate, and nothing imports it.
- A spec in `pending_review` is green because its file is named in a list of allowed failures; a module id that is not in that table is allowed the same failure by default, with no backlog item.

### 2.3 An approval is not bound to anything

Beyond FB-258 (the hash leaves out the whole `integrity` block; a first hash is "approved" with no approver; any name is accepted):

- `forge governance approve` runs no runner. A spec failing two checks was approved and fails afterwards.
- `forge governance stamp` on unchanged content rewrites the recorded schema version and hash and keeps the approval. So a schema can be edited, its frozen copy and registry entry edited to match, every spec re-stamped, and all of them remain approved by the owner without `approve` being run (done on a copy with 28 specs).
- With `spec_hash` blanked on an approved spec and its content changed, `add_spec_hash` ends in "approved" with the approver kept.
- A released schema file edited in place is not noticed by a run or by `approve`: both compare the registry with the spec, never the file. Only `registry_problems` notices, and only `forge governance schemas` and the tests call it.
- A schema registry file carries no hash of its own. A governed list records a schema version that nothing compares.
- The states `modified` and `reverted` are written only by library functions; no command produces or resolves them.
- No run is recorded: the table `governance_reports` exists in a migration and nothing writes or reads it.

### 2.4 What is governed is not a closed set

- The seven object schemas under `forge-hub/fxts/fvts/objects` have no hash of their own, are not listed, and are not in the hub's schema registry, though the framework's document says they are as the one schema registry knows them. One changed incompatibly under the same `v1` passed 21 of 21.
- A second copy of forge-mes's adapter spec is tracked under the interim MES bridge, approved, different from the governed one, and not listed.
- Files the governance command does not see, with the tests green: an adapter spec under `docs/`, a spec loose in an `fxts/` folder, one in a sub-folder, a module spec in an adapter folder (run as an adapter spec), a folder for a framework that does not exist.
- Two specs of one name in two folders: the hub's is returned silently; only a test looks for duplicates.

## 3. The real thing, measured

### 3.1 The hub's API (FATS)

- 22 of the hub's 50 API routes have no spec, among them every route that writes back to a module and all nine curation routes.
- 16 of 26 specs declare authentication required, and the route answers without credentials with authentication enabled: listing and registering adapters, ingesting records, the registry's read routes, the context routes. The eight scoped write routes do refuse.
- All 28 specs declare one error format; the deployed app returns another (the handler is installed only in an app nothing deploys).
- Every spec declares a rate limit; the deployed app has no limiter (80 calls against 30 a minute, none refused).
- Ten routes take a body and no spec names a body schema. One route requires a query parameter its spec does not declare.
- What a spec cannot declare at all: the permission a route needs, the response body, error cases, pagination, idempotency.

### 3.2 The transport (FTTS)

- The spec's error mapping is wrong against the real servicer: an unknown module, invalid fields and a call before Register each return INTERNAL where the spec says NOT_FOUND, INVALID_ARGUMENT and FAILED_PRECONDITION.
- Ingest with an unknown session id returns success.
- Refusal causes exist only as prose. The module side recognises two clock causes; `time_governance_missing` becomes a plain error and is not put on health. No retry or back-off exists on the module side.
- Six of the twelve RPCs are not overridden by the hub servicer.
- Nothing of the signed transport contract can be declared in the spec or its schema: keepalive, deadlines, buffers, expiry, deduplication, data classes, contract version, reactions.

### 3.3 The modules (FACTS, FMTS)

- **Context fields disagree in all nine modules.** Each can emit fields its spec does not declare (1 to 6). In four, required fields are absent on a record from an empty event. Per record, the hub checks the manifest's list, not the spec's, and a missing field is only counted. `AdapterBase.validate_record` has no caller.
- **Seven of the nine modules are stubs.** None calls its source system; eight import no client for the protocol they declare. Their passing module specs describe forge-core's transport fed with fixture events.
- Eight specs declare backfill; no module returns a backfill record.
- The lifecycle and error-handling sections (timeouts, restart policy, back-off, circuit breaker, dead letter, health degradation) are read by no code.
- Configuring forge-historian with the parameters its spec marks required raises a validation error.
- forge-ot's manifest against its spec: no connection parameters (the spec lists 12), one authentication method (three), a health interval of 5,000 (10,000); its `manifest.json` has no time governance and its module spec declares no database while it opens a local one.
- Six modules declare a read-write hub database they have no code for.
- No module reads its own spec.

### 3.4 One clock, in modules with approved specs

- forge-historian and forge-ims stamp a time with no zone as UTC, and the kit passes them. forge-cmms, forge-nms and forge-integ-erp-netsuite also accept a time with no zone.
- forge-ims drops an event with no time and forge-wms an event with a zone-less time; both stay healthy with no refusal reported.
- forge-wms and forge-nms each have a path that substitutes the current time; whether it is on the collection path was not checked.

### 3.5 The conformance kit

- It runs in process, not over gRPC, and injects one failure (a clock five seconds out). A refused Register, any other refusal, Stop, Subscribe, Write, Backfill and Discover are not exercised.
- An empty adapter shell passes three of its four checks; a shell that overwrites the source time with the current time passes the fourth.
- It imports the installed package, not the files of the checkout it is given. It cannot drive the interim MES bridge (FB-155). One module's time check never ran for lack of a fixture, and its spec is approved.
- 44 waivers across nine modules; each has a reason and a backlog item; nothing fails when a waiver is no longer needed, and three ways of closing a backlog item are not recognised as closed.

### 3.6 Views, objects, widgets, lists

- The hub's real output fails the object schemas: health components, the module list, governance rows, all fifteen schema rows. User, role and role assignment have nothing that produces them. One declared action matches no route.
- A tag path is not checked unless a write configuration is passed, and the command passes none: made-up paths pass.
- Vacuous passes: a golden set in which every message is skipped; a list with no items; a screen with no children; a view over an unapproved view spec.
- Golden files are hand-written inputs with no expected output; the check is that rendering raises nothing.
- Four governed lists do refuse a value outside the list (proved). The hard-limits list is enforced by nothing (FB-233).

## 4. What held

- All 70 governed specs and lists carry a hash that verifies; the governance command lists exactly those 70; 69 are approved.
- Every cross-reference between view, object, widget and action resolves.
- The enum parity check between specs and the Python models is a real comparison.
- The proto agrees with the transport spec today, and every module's schema reference agrees with its code, though no check holds either.
- The two verdicts (the hash verifies, the hash is approved) are produced by all six frameworks.

## 5. Not checked

The Go code and the interim MES bridge's runtime behaviour; the OT routes and forge-ot's behaviour (nothing of it was run); latency; whether the 73 conformance tests the transport spec counts exist; branch-protection settings; the full test suite under the experiments on the copy.

## 6. Where the proof is

The audits' scripts and outputs were written to the session's scratch folder and are not in the repository. Each becomes a real test when the fault it shows is fixed (the mutation that passed is the test that must fail), or it is not kept.
