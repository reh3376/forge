# The integration module builder — design record

**Status:** approved by reh3376 on 2026-11-18 (the owner answered Q-1 to Q-9 one at a time and declared the answers the signature; the status line was set on that word) · **Backlog:** FB-154 (with FB-142, FB-153) · **Roadmap:** decision A-18
**Participants:** reh3376 (owner, decides and signs), Claude (asks, records, proposes)

Every statement is tagged **[OWNER]** (decided by the owner, with the date), **[FACT]** (what the code or a signed record says today) or **[PROPOSED]** (Claude's recommendation, not approved).

---

## 1. What the owner decided (2026-11-18)

**[OWNER]** "The integration modules will be built for very specific 3rd party applications, while the general framework of an integration module can be defined the actual way it functions will vary greatly based on the 3rd party application it is integrating with. Because of this the integration modules will need to be able to be defined and built by the dev users of forge, so we should ensure the proper infra is in place to allow users to build these integration modules once forge is up and running at a given install. This type of builder will be low-code with a designer that allows the user to customize the integration module as necessary to meet 3rd party app requirements, with drag and drop and scripting. The designer will look and function similar to the Ignition perspective designer with aspects similar to node red where you can chain function blocks together to build the necessary custom functionality integration with 3rd party applications requires."

**[OWNER]** (2026-11-18, with the signature) "The FxTS specs govern the way the builds can occur, the person designing a given custom integration module is bound by the specs, only a hub admin, dev, or superadmin can make changes to the actual FxTS schema. A user can only build within the defined specifications for that module type."

**[OWNER]** (2026-11-18, after the signature) "Users can request modifications that will then go into the forge support CI/CD pipeline for review."

Also in force: integration modules are named `forge-integ-<system>` (A-17); management modules are built before integration modules, and forge-display before both (A-14); every module meets the forge module requirements (D-12); every repeatable process has an FxTS spec (A-13).

## 2. What exists today

- **[FACT]** No designer, no flow format, no runtime that executes a user-built module.
- **[FACT]** The module requirements and the FMTS framework were written for modules built from the SDK and declared in a hand-written spec.
- **[FACT]** The OT module has a Python scripting SDK; nothing else in Forge runs user scripts.
- **[FACT]** forge-display, which renders every Forge interface (A-3), does not exist yet.

## 3. Design

From the owner's answers in §4 (2026-11-18). All of it is **[OWNER]**.

| # | Decision |
|---|---|
| B-1 | **The integration host.** Forge ships one Go program that loads a flow and becomes that integration module: it registers with the hub over gRPC under the module's own id, `forge-integ-<system>`. Export of a proven flow as generated Go code comes later and must behave identically (Q-1). |
| B-2 | **A flow is a governed spec.** Blocks, wiring, scripts and connection settings are one document with a version and a hash. Every saved change is a new version (Q-8, A-13). |
| B-3 | **Blocks.** A Forge library of compiled blocks (sources, transforms, timing, sinks) plus script blocks. No code from outside Forge is loaded into the host (Q-5). |
| B-4 | **Scripts.** Python, sandboxed with time and memory limits, reaching only the Forge scripting API. One sandbox and API for the OT module and the host (Q-4). |
| B-5 | **The module requirements apply in full.** The designer generates the module's FMTS and FACTS specs; the host supplies the time exchange, failing closed and health with causes; the conformance kit passes before the hub admits the module (Q-3). |
| B-6 | **Approval is per hub.** An installation's approvers hold an approval scope on a hub. Roles are scoped by hub, each hub independent; one enterprise-wide super admin holds every scope on every hub (Q-2). |
| B-7 | **Credentials come from forge-creds.** Entered once in the designer, held by forge-creds, referenced by name, handed to the host at Configure, never readable by a script (Q-6). |
| B-8 | **The designer is forge-display's design mode.** One UI module (Q-7, A-3). |
| B-9 | **Lifecycle.** Test mode with nothing reaching the hub's stores; promotion of an exact approved hash; rollback by promoting the previous one; all audited (Q-8). |
| B-11 | **The specs bound the builder.** The FxTS schemas for a module type define what can be built. The person designing an integration module works inside them and cannot change them: only a hub admin, a dev or the super admin can change an FxTS schema. The designer offers only what the schema of that module type allows, and a flow outside it is not a valid spec. |
| B-12 | **Changes outside the specs are requested, not made.** A user who needs something the specs of a module type do not allow requests the modification; the request goes into the Forge support CI/CD pipeline for review. The pipeline and where a request is filed are not designed. |
| B-10 | **The integration section of the FMTS spec.** Product and vendor, supported versions, interfaces, direction, site owner, credential name, clock read (Q-9, FB-153). |

**Order.** Nothing here is built before forge-display (A-14) and the management modules. What it needs from work already planned: forge-display's design record covers design mode (FB-143); the conformance kit can drive a module in another process (FB-155); the role model gives per-hub scopes, the super admin, and the hub admin and dev roles that may change a schema (FB-075); a schema change is versioned and changes a hash (FB-151); forge-creds has its own record (FB-142); the FMTS schema's next version carries the integration section (FB-153) under the versioning rules (FB-151).

## 4. Questions for the owner

| # | Question | Answer |
|---|---|---|
| Q-1 | What is a user-built integration module when it runs? | **Answered 2026-11-18: both, the host first and generated code later.** A built module runs in one generic integration host that Forge ships (a Go program that loads the flow the user built and becomes that module: it registers with the hub under the module's own id and meets the module requirements). A module that proves itself can later be exported as generated Go code. Debt check: two execution paths must give the same behaviour, so the flow definition has to be the one source for both and the conformance kit has to pass on both; the export is built only when a module needs it. |
| Q-2 | Who approves a module built at an installation? | **Answered 2026-11-18: the installation's admins.** The flow is hashed and stamped like any spec, the hub admits only an approved hash, and every approval is audited. The owner's words: "1 is the correct answer here, but I want to point out that each hub must be independent as far as role permissions are concerned. The approver for one hub may or may not be the same for a second area hub on the same site. There should be a super admin that has full access to all hubs in an enterprise but the rest of the roles need to be scoped by hub." So approval is a scope held per hub; one enterprise-wide super admin role holds every scope on every hub. Debt check: this is a statement about the role model as a whole, not only about the builder; it is to be checked against the signed roles record (`docs/decisions/roles.md`, R-7 scoped assignments, R-16 and R-18 the managing hub) and carried into FB-075. |
| Q-3 | Do the module requirements bind a built module in full? | **Answered 2026-11-18: in full, and the designer does the work.** A built module is a module like any other. The designer generates its FMTS and FACTS specs from what the user configured; the host supplies what every module needs (the time exchange, failing closed, health with causes); the conformance kit runs before the hub admits the module. The user sees a checklist, not JSON. Debt check: the kit must be able to drive a module in the host (FB-155), and the specs the designer generates are the same formats a person writes, with no second dialect. |
| Q-4 | Scripting: the language, the sandbox, what a script may reach. | **Answered 2026-11-18: Python, sandboxed, the Forge API only.** A script runs in a sandbox with time and memory limits and reaches only what a Forge scripting API gives it: the data flowing through its block, the module's own configured connections, logging and the record builders. No file system, no arbitrary network, no imports beyond an allowed list. Debt check: this is the model of the OT module's scripting SDK, so one sandbox and one API serve both, and a script cannot read a credential (Q-6). A third-party system that needs something outside the API gets a new block from Forge, not a hole in the sandbox. |
| Q-5 | The function block library, and how a block is added. | **Answered 2026-11-18: a Forge library plus script blocks.** Forge ships a governed library of blocks written in Go inside the host: sources, transforms, timing and sinks. A user adds behaviour of their own only as a script block (Q-4). New compiled blocks arrive with Forge releases. Debt check: no code from outside Forge is ever loaded into the host, so there is no plug-in format to secure or keep compatible; the cost is that an unusual system waits for a Forge release or is handled in script. Installable block packs and user-composed blocks were offered and not chosen; they stay possible later without changing the flow format. |
| Q-6 | Credentials for the third-party system (FB-142). | **Answered 2026-11-18: forge-creds issues them at Configure.** forge-creds is the one credential authority, with an existing secret store behind it. The user enters a credential once, in the designer, and it goes straight to forge-creds. The module's flow and specs hold only a reference by name. The hub hands the secret to the host at Configure, short-lived and in memory only; scripts cannot read it. Rotation and every access are audited. Debt check: this settles FB-142's direction for integration modules; forge-creds still needs its own design record (what else it holds, how it starts before the modules it serves, the store behind it). |
| Q-7 | Where the designer lives, given that forge-display renders every interface (A-3). | **Answered 2026-11-18: a design mode of forge-display.** forge-display has a run mode (render the screens modules describe) and a design mode (author things). The integration designer is one design-mode editor, beside the screen editor forge-display needs for HMI screens. A-3 holds: one UI module. Debt check: forge-display's scope grows, and its design record (FB-143) must cover design mode from the start, or the designer would be bolted on later. |
| Q-8 | How a built module is versioned, tested, promoted and rolled back. | **Answered 2026-11-18: versioned, tested, then promoted.** Every saved change is a new version of the flow with its hash. A version runs first in a test mode, against recorded sample data or the real third-party system, with its output inspected and nothing reaching the hub's stores. The conformance kit must pass. An approver (Q-2) promotes that exact hash to production; the hub runs only promoted versions; rollback is promoting the previous approved version, one action, audited. Debt check: test mode must be a property of the host that the hub can see, so that a test run can never be mistaken for production data; a separate development hub was offered and not required. |
| Q-9 | What the integration fields of the FMTS spec must hold (FB-153). | **Answered 2026-11-18: this set.** The product name and vendor; the product versions the module supports; the interfaces it uses; the direction (read, write or both); who owns the system at the site; the credential it needs, by name; how the system's clock is read. They form the integration section of the FMTS spec in its next version, required for kind `integration` and absent for the other kinds; the designer fills them. Debt check: the clock-read entry already exists in the time contract and is not declared twice; a spec names a product and vendor only at an installation, never in this public repository (A-16). |
